# Plan writing

Use the owner's selected destination and established project layout throughout.
Any `docs/specs/NN-slug/` path below is a default example, not a location
requirement; preserve the selected effort's metadata and stream relationships.

Read the approved spec and actual source seams before planning. A plan promises one spec, not a substitute spec invented from research. Missing spec blocks coverage claims unless the owner explicitly declined it and the limitation is recorded. An existing reviewed plan requires revision/supersession authority, never blind overwrite.

## Scope and recovery

Before work and after resume, read the current brief, selected progress authority, latest decisions and effective project instructions, then inspect actual source and retained outputs. Existing valid approval continues within scope; changed scope or a real unresolved choice needs coordinator decision. Leaves return complete evidence and stop, without delegation or shared-state writes. Stage completion admits no successor, publication or cleanup. No silent model/provider/protocol/isolation fallback.
## Folder layout

Use the project's actual layout/tracking policy; never add a specs ignore rule. One effort has one synthesis; each independent stream has one spec and one plan. Record filenames in parsed meta.yaml only after authorized files exist; before then plan is null. Link actual upstream mission/receipt references rather than ticket seeds; metadata is not a task ledger. Coordinator alone updates this shared metadata. A spec-declined stream records the explicit decision. Verify both directions: every named file exists; every spec/plan is named.

## Solution ownership and semantic traceability

Owner-facing recommendations, questions, waits and optional upstream offers in
this guidance belong to the coordinator. A Pi leaf returns evidence, unresolved
interpretations and consequences through its existing supervisor/return route
and stops without prescribing a remedy or next stage.

Consume the actual accepted spec and current source. Choose the technical
solution within inherited constraints; distinguish provenance-bearing owner or
consumer restrictions from planner choices and explain consequential tradeoffs
near their rationale. An approved legacy internal design remains consumable as a
constraint; do not infer missing behavior from its implementation proposal or
require a cosmetic migration. Do not treat delegated routine choices as missing
requirements or invent a mandatory count of alternatives. A changed required
outcome needs an explicit spec revision. Required public formats/signatures stay
exact even when private mechanisms are open.

Link every requirement to contributing tasks and completion checks; inspect the
meaning, not just ID presence. Preserve obligation, permission, prohibition,
actor/scope, triggers, conditions, bounds and exceptions, retaining stable IDs
through harmless edits. Coverage expresses intended contribution, not verified
satisfaction. Each task has an independently checkable outcome, owned surfaces
and relevant consumed/produced interfaces or deliverables.

Explain each dependency using consumed deliverables: `start` inputs must be
accepted before authoring; `join` inputs are needed only at integration or
verification. Runtime behavior order alone is not build order. Parallel readiness
needs accepted inputs, disjoint ownership and checked isolation/settlement, not
merely separate task names. Graph views project these same relationships without
becoming a second mutable status authority; preserve serial J/C/R barriers.

Preserve and show the spec's resulting vocabulary, boundary and invariant
clarifications, and identify new clarification introduced by planning. Do not
merge concepts merely because they share a word in different contexts: finalized
payment settlement and terminated worker/process settlement remain distinct.
For a small prose correction, preserve why no tactical modeling is warranted.

Resolve routine choices from source and record compatible low-impact reversible
observable defaults as agent choices. Reuse valid decisions; consequential
unresolved goals, scope, external contracts, security, preservation, irreversible
commitments or material cost need evidence, recommendation, consequences, a
concrete distinguishing example and an actual owner answer. Expose unavailable
required inputs and affected claims rather than inventing approval.

Surface new or materially expanded verification machinery or hard gates not
settled in the spec as consequential owner choices: protected purpose/value,
evidence, scope/useful granularity, time/cost/maintenance burden, exact blocked
stage/condition and simpler alternative (including informational comparison).
Recommend, show a concrete example, ask one question and wait before adoption;
keep the proposal unresolved while continuing unrelated authorized work. Never
silently turn a proposed evaluator, run matrix or subjective threshold into a
requirement. Reuse approved policy and required project checks without repeated
permission; ordinary relevant test choices remain agent-owned.

Pi leaves return evidence, unresolved interpretations and consequences through
the existing supervisor/return route, without prescribing a remedy or next stage.
The coordinator owns recommendations and consequential owner questions/waits.

## Write a buildable plan

Start with goal, architecture, tech stack and exact global constraints. Map every requirement to a task and acceptance check. Each task names owned files, source anchors, consumed/produced interfaces and predecessor dependencies. Fold scaffolding and documentation into the smallest independently testable deliverable. Split only when ownership and evidence can be independent. Record a testing strategy and rationale in each existing task brief. Select `critical-tdd` for new or changed auth/secrets, migration/removal, ownership, concurrency/settlement/isolation behavior and reproducible behavior bugs. Plan an actual tdd-pi read and short public-behavior slices: an invented-data test, observed intended failure, minimal implementation, green and relevant negative/legacy regressions. Other features and behavior changes default to the same TDD loop; a different strategy needs a concrete reason and owner agreement unless already approved by task/project policy. Pure behavior-preserving refactors stay green on existing coverage and characterize uncertain legacy behavior before restructuring. Routine prose/manifests/mechanical wiring without a changed safety invariant use `focused-postcheck`: exact diff inspection, positive/negative cases and approved focused checks after editing. Explicit test-first requests and project-required checks govern. Preserve existing safety tests; never manufacture red cycles per file/task or prose-substring tests. If strategy is absent, apply tdd-pi defaults and record the selection in the existing brief/handoff; only genuine classification conflicts or proposed exceptions need an owner decision. Include a scoped commit only if authorized. Include real code/commands/expected outcomes where known, not “handle edge cases”, “similar to task N” or undefined signatures. Distinguish consequential unresolved decisions from delegated design; do not pretend agent choices are owner-fixed.

## Behavior-sized tasks and briefs

Each implementation task delivers exactly one observable outcome at one interface seam. Record its stable task key, one owner, changed or exercised seam, acceptance point, exact owned paths, predecessor inputs and identities, bounded initial context, selected testing strategy and authorized initial checks, stop and non-prescriptive return conditions, and durable handoff consumed by successors.

A task is not one schema field, function, file, unit test, manifest bump, or documentation edit. Group those details when they jointly deliver the same behavior and acceptance point. Split only when ownership, predecessor inputs, and acceptance evidence are independently useful. Merge tasks that share a seam, unresolved decision, paths, or repeated partial-state exchange, or whose coordination cost exceeds useful parallelism. A parallel-ready set contains only predecessor-complete tasks with disjoint ownership and no unresolved shared design choice. Reject both microtask fragmentation and a task that hides independently ownable outcomes.

Initial context is limited to the approved spec section, predecessor interfaces, relevant source anchors, project instructions, acceptance point, and authorized commands. It is not an accumulated transcript or a static prediction of every future read. Keep plan-generated child briefs simple: outcome and acceptance point; exact source/base and subject identity; owner and owned paths or read-only subject; predecessor interfaces; bounded initial context; selected strategy; authorized commands and applicable host/resource limits; output binding; stop and non-prescriptive return conditions; and upstream mission/run/receipt references when applicable. Reference shared approved evidence rather than duplicating it.

Do not introduce packet loaders, global read/skill binding tables, per-child `requiredSkills` arrays, read-key graphs, rubric hash tables, or perfect-context prediction. Children still read current mandatory briefs, native state, project instructions, and selected guidance required by their effective role.

When a task stops, it returns only observations, evidence attempted, unresolved questions or shortfalls, newly discovered requirements, confidence, and consequences or risk if unresolved. It must not suggest, request, name, initiate, or semantically prefer paths, commands, context, budget, scope, specialist, model, provider, or escalation/remedy/package. The parent owns any later decision.

Include negative paths, migration/rollback, authority boundaries, applicable host/resource limits and a durable handoff. Retain required fresh independent whole-change implementation review even for small deliveries; only the owner may explicitly waive it. Preserve Pi's ban on task-by-task two-cycle review rituals. Task count does not justify fanout. Single-stream risk assessment belongs to plan-execute-pi; disjoint lanes may use plan-execute-parallel-pi after explicit execution/delegation authority. The coordinator selects execution mode once at plan acceptance, using plan-execute-pi for sequential/inline or phase-separated write/integrate/validate operations, and plan-execute-parallel-pi for independent disjoint owners. Plan reviewers do not select mode. No mandatory new root numerical budget or form is required; existing runtime concurrency/spawnLimit/timeouts remain. A plan saved locally is not a claim of remote availability.

## One progress authority

At plan acceptance the coordinator records the sole mutable progress authority once in the existing plan/brief. Native mission/workflow state that actually owns delegated runs remains authoritative, including recovery; a project tracker receives references, not mirrored status. Without run-owning native state, explicit project/owner selection wins, otherwise use the existing tracker or one durable plan-associated record. A native UI todo alone does not override the project tracker. Plan checkboxes describe intent, metadata indexes artifacts and logs retain observations; do not expand checklists into mirrored todos, tk tickets or another ledger. Respect actual ignore/tracking policy. Seed tickets once only if the tracker is selected and writes are authorized.

## Review and handoff

Perform the author coverage/placeholder/type/name check inline, not through a dispatched self-review. The coordinator admits one independent plan-review-pi reviewer for every written plan, including one task, unless the owner explicitly declines that subject and the existing brief records it. No automatic second-model discovery or consent loop. Inline self-check does not substitute for independent review. A valid pre-existing planning grant continues; plan acceptance does not authorize execution. Report exact hashes, open decisions and the next authorized stage.

## Review disposition

Use plan-review-pi and its plan-reviewer.md for the exact subject and consequence-based disposition contract. One reviewer and one batched bounded correction are the default; Critical/Major or more than two distinct Medium block, and one or two Medium residuals require explicit owner acceptance. Demonstrated fixes are parent-verified, not independently re-reviewed; changed interfaces/invariants/acceptance or insufficient proof require owner decision/additional grant.
