# workflow-implement-pi

Invoke `/skill:workflow-implement-pi <request.json>` from the authorized parent.

Disjoint native/Claude/Codex writers → separate native integrator → native validation. Each writer uses `worktree:true` and the same approved clean named `baseRef`; the parent verifies it resolves to `sourceRevision` before launch. Explicit file claims must be disjoint and included verbatim in authorization.files. Both upstream external writer choices may be selected together. Missing/unavailable requested writers fail the entire request before any spawn, never disappear into omissions or a native replacement.

The parent supplies a separately owned persistent `integrationCwd`, verifies its clean named base, exclusive ownership and source revision, includes it in sourceRoots and excludes all temporary managed worktrees. This checkout survives writer cleanup for the native validator. Every writer returns upstream captured patch/handoff references. Integrator reads those manifests and patches, not transient branches, before applying; validation reads the exact aggregate and runs the explicit authorized commands through native tools. Claude writer has Read/Write/Edit/Glob/Grep only, no Bash/MCP: it cannot perform required test commands. Codex writer uses workspace-write with approval never. Both require qualified existing CLI/auth/contract observations.

Preflight managed-cleanup authority for the exact runtime allocation policy, capture and deletion semantics; no per-child microapproval is needed inside the existing grant. Unknown cancellation/capture ownership retains evidence for parent reconciliation. Outputs writer-<key>.md, integration.md and validation.md live outside source/integration/worktrees; validation logs must live there too. The parent reads reports AND upstream patches/handoffs. No integration/publication is inferred from a writer exit.

## Parent preflight — required before any dispatch

This skill runs Pi **0.87.1** with **pi-subagents 0.72.1**. Read the installed upstream workflows, tool-reference and agents guides in full and their relevant cross-references. Do not upgrade or patch packages. Static catalog placement is not activation or qualification.

1. Read the actual owner grant, project/global instructions and current native mission/receipts/status. Confirm all requested stages/actions, source revision, exact file claims, validation commands, output writes, provider spend and isolation/cleanup are authorized. `authorization.parentVerified` records that check; request JSON cannot grant authority. Stop on missing or changed scope. Leaves never delegate.
2. In the exact request environment/cwd perform this **non-inference** discovery list: `command -v pi`, then `pi --version`; `command -v claude`, then `claude --version`; `command -v codex`, then `codex --version`. Run each version command only after successful executable discovery. Resolve executable identity, record time/version/omission and compare with the pinned adapter contract and existing qualified version matrix. These commands do not prove authentication or tool capability. Never read credentials, print secret environment values or launch a prompt as an auth probe. Use existing nonsecret, version-qualified successful-auth evidence when available; otherwise status is `unverified`, not `available`. Launch an unverified engine only with an explicit scoped grant recorded as `allowUnverified:true`; a failed launch stays failed on that engine. Unsupported CLI/flags or missing executable is `unavailable`, with a reason. Do not repair, install, substitute models/runners/protocols or silently retry.
3. Discover `subagent({action:"list",capabilities:true})` and inspect effective definitions/overrides, selected skill union, loaded extension providers and actual child tools. Verify each `roles` identity maps to the intended native Pi role, not a same-name shadow with a different runner/tools. Verify external identities resolve to the upstream code-owned adapters. Capabilities listing alone proves neither auth nor successful loading. Missing required role/tool/provider blocks before launch. Web needs the four activated web tools and pi-web-access 0.35.0; local roles do not acquire MCP by prose. Optional code-intel is separately qualified; missing services use explicitly disclosed authorized source reads, never private/shared service startup or retargeting. Keep the sandbox 0.71.0 qualification separate.
4. Canonicalize cwd, integration checkout, all source roots and managed-worktree roots using filesystem realpath/symlink resolution. For a new outputDir, resolve the nearest existing ancestor and append only validated ordinary path components; recheck after creation. Create a unique durable output directory **outside every source, integration and managed-worktree root** and check ownership, writability and no preexisting output claims/symlinks. Include all those canonical roots in `sourceRoots`. This library deliberately uses the default external durable location, not the optional in-source `.pi/subagents/` exception. Never clean, stash or ignore source paths to admit outputs. The sandbox's lexical checks enforce supplied assertions only; they cannot inspect symlinks, Git or authority. Parent must retain reports and upstream patch/handoff manifests before runtime retention expires.
5. Check actual RAM/cgroup headroom and provider budget: start with at most two useful lightweight lanes on 2CPU/4GiB, reserve 500MB and admit an expensive job only with at least 750MiB headroom; one expensive build/test job under the project lock. Unknown/insufficient resources block expensive admission. Bound concurrency (1–2), total spawns (1–12), and timeout (at most one hour) before launch. There is no custom scheduler, second ledger or always-on goal-controller guarantee.

`runners` handles every supplied candidate: `available` requires existing nonsecret auth evidence, discovered executable/version and verified adapter contract; `unverified` requires explicit launch authorization; `unavailable` cannot launch. Missing/invalid selected status fails before spawning. Peer review additionally requires records for all three candidates so omissions cannot disappear. Every return names requested, selected and omitted engines/reasons, source revision, canonical output location, limits and child receipt/report references. No tool/model/acceptance/schema fields are injected into external runners. Claude read-only has **no tools**, user-only settings/hooks are an operator-trusted prerequisite, and empty MCP; Codex read-only uses its upstream sandbox. Supply complete bounded inline subject/diff, requirements, rubric and test evidence, not unreadable file pointers. Both external adapters are one-shot and cannot use native supervision/resume.

## Pinned input and result envelope

Pi-subagents 0.72.1 normalizes args before the sandbox: **16 KiB (16384 UTF-8 JSON bytes) total**, nonempty strings, at most 16 properties per object, 64 items per array, and nesting depth 8. This library additionally bounds the entire inline `evidence` JSON array to **8192 UTF-8 bytes**. Field limits and total limits both apply; JSON escaping and multibyte characters consume the byte budget. Schema character limits alone cannot enforce UTF-8 totals: run the actual pinned `normalizeWorkflowArgs` through the native launch boundary, not a substitute validator. Use `authEvidence:"UNVERIFIED"` for unverified auth, with the separate explicit `allowUnverified` grant; empty strings cannot cross the upstream boundary. Unavailable executable/version observations use the nonempty `UNAVAILABLE` sentinel. Available auth cannot use either sentinel as proof.

No-tool external review is only of the complete small inline subject that fits that envelope, not an entire large repository/diff. Narrow the authorized review subject before launch and disclose omitted scope; do not truncate evidence silently or evade limits via filesystem/host access unavailable to the peer.

The 0.72.1 external awaited result can omit `outputReference` after a successful save. The compatibility path requires the exact expected engine/key/run-associated async directory, structured adapter identity/log references, a single underlying exit-zero result without save/artifact/error/partial signals, and the exact runtime saved-output summary for the bound path. A summary alone is never sufficient. Raw output, underlying results and original references remain in the return, alongside binding provenance and `filesystemVerified:false`. The derived path is a candidate for the next native stage and parent to **read and verify**, not a claim that the sandbox inspected bytes. Missing or ambiguous evidence blocks; no model-authored save claim repairs a real save error. The pinned awaited async projection drops metadata-only observability save errors: omission does **not** prove metadata persisted. The return labels that unknown explicitly. All exposed errors and bound-output/artifact-output failures are rejected. Optional observability metadata is distinct from required evidence: absent/malformed bound output or required handoff/patch still blocks parent acceptance/integration.

Native verdict stages deliberately combine a required `output` path with `outputMode:"inline"` and `outputSchema`. In pi-subagents 0.72.1, `structured_output` can end the child without assistant final text; `file-only` settlement can therefore reject the child before the runtime persists the structured JSON. Inline is only the return transport for those verdicts: the runtime must still save the same bytes to the bound path and return the exact `outputReference`, or the workflow blocks.

## Execute the installed artifact, not a generated orchestration

Resolve `{skillDir}` to the absolute installed skill directory (local installs may substitute a project-relative path). Read `request.schema.json`, parse the request file outside the sandbox, validate it and complete the preflight above. The `fixtures/request.json` packet is invented test data, **not a launch grant**. Replace observations with actual verified evidence; never copy its available/auth assertions into live requests.

First call `subagent` with `action:"validate"`, the absolute installed `workflowScriptPath` ending in `/workflow.js`, and the parsed request as `args`. Then make **one** top-level call with the same path/args and:

- `cwd: request.cwd`, `async:true`;
- `globalConcurrencyLimit: request.concurrency`;
- `maxSubagentSpawnsPerRun: request.spawnLimit`;
- `timeoutMs: request.timeoutMs`;
- explicit `mission:{title:<bounded authorized effort name>}` (strict persistence; no `mission:false`).

Do not set top-level model/tools/skills/acceptance/outputSchema defaults: they would leak native contracts into external children. The parent top-level `globalConcurrencyLimit`, `maxSubagentSpawnsPerRun` and `timeoutMs` are the actual native run controls. Args only validate/report the requested bounds. The supplied per-child `timeoutMs` is not a total workflow deadline; without the parent deadline sequential stages could each consume that duration. No second controller is added. Scripts omit child `async:true` so awaits yield final results. Args are frozen, persisted, nonsecret data; no imports, filesystem, Node globals or `runs.host` are available in these scripts. Request fields are documented by the schema and runnable fixture. Cross-field validation, file-claim checks and status handling are also enforced by workflow.js before the first spawn. Dynamic bindings are not authority proofs.

## Completion and recovery

Await native completion notifications; do not poll. A child runtime without notifications may use bounded `bg_wait` only when it needs results. Inspect exact native status/terminalOutcome and receipt path, then **read all saved report bytes**, verify hashes, patches, test logs and unchanged review subjects before accepting. A `ready-for-parent` result is not acceptance. Structured reviewer verdicts are evidence claims, not independent external facts. Failure, timeout, cancellation, detached work, missing outputs or failed dependencies blocks later stages; no silent replacement. Native timeout/stop owns continuation and retains partial receipts/uncertain worktree ownership. Do not treat stop as permission to delete. Reconcile native mission state and latest outputs after compaction/restart before any bounded same-protocol action. Preserve necessary evidence outside retention-managed locations; never maintain a competing task ledger.

Run the model-free installed fixture with `node --test <absolute-skill-dir>/fixtures/workflow.test.mjs`. With `PI_SUBAGENTS_PACKAGE` pointing to the already-installed exact 0.72.1 package, these tests pass valid requests through real `normalizeWorkflowArgs` and exercise its validator/sandbox and save helpers with model-free results. Without that opt-in the upstream integration tests are visibly skipped. These tests execute this actual shipped body with invented final results, not model inference or auth/containment qualification. Installation/update/removal and real installed-script dogfooding remain separate parent qualification gates.

Writer admission requires an exact run-associated handoff candidate: runtime foreground handoffs/<runId>.json, or the pinned <asyncDir>/handoff.json location (asyncDir basename must equal runId) derived from that result’s actual run-bound asyncDir. An arbitrary nonempty artifactPaths list is insufficient. These candidates are not capture proof: the native integrator must read ALL manifests/patches/status/claims and verify identity, base and complete capture before ANY mutation. Missing or partial capture blocks validation. Partial cleanup can mean a retained native session, and never grants deletion. Live external writer capture remains a separate qualification gate.
