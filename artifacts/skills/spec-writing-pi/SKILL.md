# Spec writing

Explore intent, constraints and success criteria before implementation. Read existing synthesis and every supplied findings artifact first; do not rerun settled research. Confirm the implied design when evidence is complete; otherwise ask the unresolved questions one at a time. Separate unknown-domain research (research-team-pi under its own grant) from decomposition of known independent streams. Optional grilling-pi may stress-test the design within authority.

## Scope and recovery

Before work and after resume, read the current brief, selected progress authority, latest decisions and effective project instructions, then inspect actual source and retained outputs. Existing valid approval continues within scope; changed scope or a real unresolved choice needs coordinator decision. Leaves return complete evidence and stop, without delegation or shared-state writes. Stage completion admits no successor, publication or cleanup. No silent model/provider/protocol/isolation fallback.
## Design

Compare two or three approaches with tradeoffs and recommend one. Present architecture, components, data flow, failure handling and verification at proportional depth. Use compact ASCII structure diagrams when they clarify a boundary. Prefer small interfaces and existing conventions; do not smuggle unrelated refactors into design. Existing explicit design/authorship approval is sufficient within scope. Obtain decisions on actual unresolved choices, not repeated ceremonial approval.

## Author (ADR-0003)

Use the project's research-effort layout and tracking rules, not a foreign plugin layout or automatic gitignore edit. One effort has one synthesis, and each independent stream one spec and one plan. Coordinator owns shared meta.yaml. Name a spec only when its authorized file exists; plan stays null until written. Link actual upstream mission/receipt references, not a second task graph. Follow the one-authority selection in plan-writing-pi at plan acceptance; before then retain the existing authority. Native state owning runs wins over a project tracker, while UI todos alone do not. No checklist-to-todo/tk mirror or mandatory root numerical form. Record a user-declined spec explicitly rather than invent it. Validate parsed metadata against actual files in both directions.

Write testable requirements with IDs, scope/non-goals, interfaces, failure/rollback, authority and evidence limits. Check placeholders and contradictions inline. When a spec exists, the coordinator admits one independent spec-review-pi reviewer. Use [spec-document-reviewer-prompt.md](spec-document-reviewer-prompt.md) as a supplement to that same reviewer, never a dispatched self-review or second loop. Preserve the explicit owner-declined-spec ADR-0003 exception. No automatic second-model discovery or repeated consent. Spec authors are leaves and return their complete artifact to the coordinator. Spec completion never silently starts planning or coding; an existing valid planning grant can permit the next stage after the evidence gate.
